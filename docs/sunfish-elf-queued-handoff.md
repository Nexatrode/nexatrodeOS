# Bounded handoff after the ELF locator reply queues

Follow-up to [IMG_9712](sunfish-post-elf-mcfg-IMG_9712.md), November 24, 2026. The current original write/final ACK and ELF reply complete, MCFG's observed missing-file reply completes before its client closes, and WLAN/WLFW remain absent. Repeating the MCFG probe would not resolve the remaining startup gap.

## Evidence and the selected change

The successful saved Linux locator capture associates a 60-byte lookup with an 88-byte reply and matching completion in 374 microseconds, then observes the first WLAN firmware RRQ about 692 microseconds later. This association is supported by names, sizes, order and intent identity, not captured QMI transaction bytes. Its clocks are not spliced into the native timeline. In native IMG_9712 the exact ELF request-to-publication span is 3.729709 seconds: 3.286263 before queueing and 443.446 ms queued. The exact GLINK completion follows publication by 543.137 ms.

The earlier notes already identify registry predecessor/queue delays. The existing two-request handoff runs when a newly queued older reply leaves another request blocked. Once the exact ELF reply itself queues, there may be no remaining ELF request in the service request queue, so that handoff finishes. The normal service pass then runs RMTFS and IPA/client steps before its next outer router continuation. The new change addresses this **post-queue boundary**, not all 3.286 seconds before admission and not a proven private-modem deadline.

The optional `sunfish-elf-queued-handoff` feature arms a private opaque request capability only after normal successful queueing of the exact first ELF lookup. The runtime asks for at most one ordinary Router/Owner dispatch immediately after registry service (including its existing older-reply handoff), before storage/IPA service work. It uses the normal bounded receive/write loop. It does not select ELF ahead of a grant or QRTR credit, invoke a device restart, bypass a pending client-close decision, or relax any validation.

The router first checks its terminal/reentrancy state, continuation, other-owner bits and exact Owner/generation binding. Owner checks live state and pending firmware/TFTP-close work. A pure Core lookup checks the opaque owner/generation/request against a currently owned, unpublished registry reply. The capability is consumed before dispatch, even if a FIFO write is blocked or no fitting remote intent exists. Subsequent attempts use the existing continuation. A reply already published or retired does not earn extra work. Diagnostic flags and clocks never arm or decide the turn.

This can move the eligible reply ahead of later service work. It cannot guarantee that the normal writer chooses ELF on that pass, a particular speedup, modem application acceptance or WLAN startup. The new panel retains the earlier phase/predecessor information specifically so a remaining pre-queue wait is distinguishable from the changed boundary.

## ELF QUEUED HANDOFF panel

All numeric values are hexadecimal. Timestamps are microseconds from runtime start; phase durations are microseconds, not milliseconds. Missing/unavailable values are `FFFFFFFF`.

- **ELF RX QUEUE PUB DONE:** exact accepted lookup, queue, full publication and matching GLINK completion.
- **RX END REG ENTER SELECT:** existing receive-pass end, first registry entry and first ELF selection.
- **PHASE US RX REG SEL QUEUE:** receive→receive-pass end; receive-pass end→registry entry; registry entry→selection; selection→queue. **QUEUE PUB RXDONE TOTAL US:** queue→publication, publication→completion, receive→publication, receive→completion. These are distinct intervals, not independent extra costs.
- **ARM ENTER END FLAGS:** successful normal queue time, attempted extra dispatch entry/end, and flags: armed=1, capability consumed=2, dispatch entered=4, dispatch returned normally=8, exact ELF fully published or completed by its end=16, dispatch failed=32. Thus `1F` means the turn observed publication; `0F` means an attempted turn returned without publication. A zero clock does not prevent flag advancement. A later normal publication does not retroactively set bit 16.
- **TURN RX TX ACK US:** the normal Owner pass's receive count, publication-progress count, acknowledged logical IRQ mask and duration. Its publication count can include control or space notifications; bit 16 and the exact ELF timestamp identify ELF independently.
- **ELF PEER OFFSET ROWS TOTAL / ELF BODY DONE CREDIT CONF:** existing exact lookup metadata, reference body match, completion and host-credit flags. Credit flags use requested=1, completed=2, published before ELF publication=4, completed before ELF publication=8; last value is the ELF confirmation request.
- **WAIT NONE PEER TXCAP FLOW / WAIT CREDIT CAP CALLS OMIT:** existing queue wait buckets 0..5 (unused/unknown, same-peer TX, TX slots, legacy-flow capacity, reference-flow blocked, reference-flow capacity), then preselection call/omission counts.
- **PRESELECT RUNS:** existing compressed transaction/name/outcome/count runs. **BLOCK TXN FLAGS WAIT PUB / BLOCK DONE YIELD FIRST:** the first exact older reply seen holding ELF's same-peer queue gate, its ownership bits and existing timestamps. These fields do not assign every elapsed microsecond to the blocker.
- **TX4 RX QUEUE PUB DONE:** existing transaction-4 clocks; **LOC RX QUEUE NAMES DONE** contains request/reply counts and per-name queued/completed masks. **LOC TMS GPS ELF WLAN / LOC PDR DUMP OTHER AVS** retain service-name counts so missing WLAN discovery remains explicit.
- **ORIG ACK ELF DONE:** original first write's final-ACK completion beside ELF completion, separate identities.
- **MCFG PEER FLAGS ERROR LEN / MCFG RX PUB DONE CLOSE:** retained first post-ELF MCFG target and its actual missing-file or other result. Error is present only for opcode 5; another opcode is not labeled success by this field. The complete option/client capture remains stored, with this panel displaying a summary.
- **OTHER KIND PEER LEN OP:** existing first other accepted request (8 exact `mbn_hw.dig`, 5 WLAN, 6 other); **MCFG W FILE READ IPA / PD STATE WLAN WLFW** are existing outcome counters. **JOURNAL N OMIT BAD** exposes bounded-window saturation; this panel does not display or reconstruct omitted traffic.

The success question is whether the turn actually publishes ELF sooner **and whether a WLAN RRQ or WLFW announcement follows**. Faster queue publication without those outcomes is an isolated scheduling improvement, not working Wi-Fi. If the largest delay remains before queueing, the phase/predecessor rows identify that separately. No physical outcome is claimed before the new image is booted.
