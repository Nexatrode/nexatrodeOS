# Bounded service-announcement receive-buffer reuse

IMG_9709 showed prompt transport consumption of the transaction-3 service-registry reply, followed by repeated 52-byte intent requests, QRTR NEW_SERVER messages, non-reusable receive returns and new grant cycles. Its exact matching RX_DONE became visible 6.556 seconds after publication; WLAN and WLFW remained zero. The omitted 56 middle records prevent assigning that whole delay to the visible cycles.

The optional `sunfish-glink-announcement-reuse` change returns a fully accepted NEW_SERVER packet with RX_DONE_W_REUSE only while a real, fully published service-registry transaction-3 reply is still waiting for GLINK completion. It examines live transmit/request state; diagnostic clocks and histories do not select policy. Earlier startup and other QRTR controls retain their previous behavior. The valid incoming control envelope, controller update and client observers must all succeed first. Retained service requests never qualify.

On a successful reusable return, the physical slot remains Available on its existing wire intent ID. A fresh internal datagram identity is allocated using the existing first-WRQ reuse mechanism, so a stale TFTP handle cannot identify a later packet. Starting a new DATA packet clears the announcement marker; only a newly accepted qualifying announcement can set it again. A later QMI registry request follows normal non-reusable return/host-entry handling and keeps its original transaction, route and completion identity.

A valid intent request can ACK an already committed, available announcement buffer without advertising another one. This follows Android's existing-reusable-buffer grant path. The ACK tracks its chosen available ID. If the peer consumes that backing while ACK publication is blocked, the pending positive ACK is withdrawn and normal bounded denial/retry handling applies. The Adapter also applies the existing checked writer’s empty-RX gate specifically to this positive ACK, both before staging and at the final validated sample before TX-head publication. Already-visible receive data therefore gets its normal servicing turn first. This does not gate ordinary QRTR credit or fresh-grant writes. Fresh reservations still advertise before ACK. A full-pool denial can convert to a grant only after the exact reusable return actually commits; a blocked one-shot return retains the existing negative-ACK fallback. Uncertain publication still quarantines the session.

The window ending does not revoke an already returned reusable buffer. It remains usable until consumed; an announcement processed after transaction 3's matching receipt then returns it non-reusable. Reset clears all receive and pending ACK-backing state. Zero and oversized requests retain rejection behavior. This is a bounded receive-lifecycle change, not a relaxation of FIFO validation, generation checks, grant ordering, QRTR credits or retained reply retirement.

## Source and offline evidence

The pinned Linux requested-intent path dynamically allocates a non-reusable buffer, advertises it and ACKs. Android first searches its reusable local intents, otherwise allocating/advertising before ACK. Therefore the old non-reusable path was not inherently invalid. The candidate uses a mechanism already supported by the modem/native first-WRQ path to reduce the repeated request/advertise/ACK overhead in the observed post-publication window. It does not establish a handset timing benefit before the next boot.

Nine actual Session tests cover 32 repeated announcements with no new advertisements, existing-buffer grants, byte-identical blocked return retry, original registry transaction identity, malformed controls, oversized requests, reset, end-of-window behavior, full-pool conversion with blocked-write fallback, uncertain publication quarantine, and consumption of ACK backing during fragmentation. One actual Adapter/FIFO test covers six cases: notification or fragment already visible, notification arriving during ACK staging, and both ordinary and wrapping ring positions. It verifies no TX-head commit before receive servicing and withdrawal of a positive ACK when the fragment consumes its backing. Its pure Session prefix is installed into a freshly attached test adapter to isolate this boundary; it is not an end-to-end boot test. The production fresh-session attach requirement remains unchanged.

The previous Core and Owner fixtures run with this feature too; their earlier startup behavior stays unchanged. Paired replay scopes and any differences are recorded in the private verification bundle rather than assuming a scheduling change must preserve all wire traffic.

Replay source refresh now explicitly checks the `replay/rust/src` paths used by the compiler. During preparation we found that the prior compact-capture capacity refresh had also copied files to the replay root; the prior paired runs therefore exercised its earlier compact capacity, while the full Owner tests and native target did exercise the final capacity. Published manifests/images remain immutable. This candidate's replay inputs are checked against actual production files before compilation.

## Diagnostic and manual boot

Profile: `native-registry-announcement-reuse-v1`. Panel: **REGISTRY ANNOUNCE REUSE**. The same 80-position transaction-3 wire log is retained: first 40 and latest 39 accepted/committed records, plus the exact matching receipt. Metadata, omitted/unparsed counts, peer-tail/receipt timings and WLAN/WLFW counters keep their documented meanings. Successful reuse appears as host TX command 14 for the announcement's original wire intent; fresh grants still show advertisement before positive ACK. No WLAN success is claimed until a handset result shows it.

Build verification binds current source, AArch64 ELF, boot payload, pinned SDK reuse, actual table-pair code, generated mappings, selected stack and capability mutation checks. The SDK is reused, not recompiled. The selected stack audit excludes TLS, indirect calls and other descendants. No handset command is run during preparation.
