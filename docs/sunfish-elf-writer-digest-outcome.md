## Saved Linux/native comparison

The existing [late-reply review](sunfish-post-elf-late-reply-review.md) already demonstrated an actual native93-byte RRQ for `/readonly/vendor/mbn/mcfg_hw/mbn_hw.dig` being consumed as `UnexpectedRequest`, with no transfer and no TFTP reply. Current source still has that behavior: the WLAN provider accepts only its firmware aliases, and the builtin server's missing-name list contains MCFG, ruleset and EFS only. The Pixel now independently identifies the exact digest path through category8, in addition to its generic OTHER PATH first-post-ELF observation.

The pinned Linux `tqftpserv.c::handle_rrq` returns ERROR1 after failed open; its original `tftp_send_error` function is extracted and compiled offline with a memory-only send stub. The produced19-byte `00 05 00 01 file not found 00` matches native `MISSING_REPLY`. No file contents, socket, modem or hardware are accessed by the oracle. The successful reference journal rejects the exact digest at187.041263seconds and retries187.712392/188.711433. WLAN firmware RRQs began178.730030,8.311233seconds earlier. This is a real native response gap, not a demonstrated cause of missing initial WLAN startup.
